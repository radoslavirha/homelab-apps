# Instructions

- API end-user documentation lives in [README.md](./README.md). Keep it up to date when adding or changing endpoints, config keys, or sources — the `updating-docs` skill owns its format. Swagger UI is mounted at `/`.

## What it does

Keeps a searchable index of one or more knowledge bases in Postgres (full-text + pgvector) and serves hybrid search over an internal REST API. Two jobs in one process: a background **indexing loop** that pulls changes from each knowledge base's source, chunks, embeds (Ollama) and stores them; and the **REST API** (`/search`, `/documents`, `/status`, `/reindex`, and the writes: `POST /notes`, `PUT`/`DELETE /documents`). It is the only holder of the database login — callers (an MCP adapter, a chat filter) go through its API, never the database.

## Source layout beyond the root conventions

- `sources/` — the pluggable seam. `SourceAdapter` reports what changed since a cursor (`upserts`, `deletes`, `cursor`, `complete`); everything after it is source-neutral. A writable source also has a `writer` (`SourceWriter`: read, write, delete one document, each one commit, refusing a stale version with `SourceWriteRefusedError`); without one, the write routes answer `501`. `SourceAdapterFactory` maps `knowledgeBases[].source` to an adapter. `sources/git/` is the one implementation: the GitHub API as a GitHub App, through Octokit; `GitSourceWriter` writes through the contents API.
- `migrations/` — numbered schema migrations, run by node-pg-migrate at startup. TypeScript so swc compiles them into `dist/`; a `.sql` file would not reach the image.
- `storage/postgres/` — the pool (`PostgresService`), `SchemaMigrator` (migrations + the config-driven part: one HNSW index per model, one row per KB), and the repositories. Rows are deserialized into the DTO classes under `dto/` (`@Name` maps the snake_case columns).
- `endpoints/github/` — Octokit, but the contract is the repo's: every Octokit response is deserialized into a DTO under `dto/`; the git adapter filters and decodes.
- `services/MarkdownChunkerService.ts`, `FrontmatterService.ts`, `RankFusionService.ts`, and for writes `NoteRenderService.ts`, `DocumentValidationService.ts`, `SecretScanService.ts` — pure logic. `DocumentWriteService.ts` is the one way to the source's writer. `markdown/` holds the per-document helpers the chunker uses (`FenceTracker`, `GithubSlugger`): stateful, so plain classes rather than providers.
- `scripts/evaluate-search.mjs` — top-5 and MRR of a running instance for given weight blends; the question set lives with the knowledge base, not here.
- `test/` — the pgvector testcontainer (`globalSetup.ts`), a database per test file (`setupDatabase.ts`) — so even unit specs on `PlatformTest.create` get a migrated schema — the test doubles (`FakeOllamaEndpoint`, `FakeSourceAdapter`, `FakeSourceAdapterFactory`, `FakeGitHubEndpoint` — a branch in memory that checks blob SHAs as GitHub does — one per file), helpers (`fakes.ts`) and a corpus. Excluded from the build.

## Rules

- **Never configure a repository name.** The git source discovers it from the App's installation (exactly one repository, or it refuses). This repo and the deployment values are public.
- **Indexing and search embed through `EmbeddingService` only**, so a chunk and a question are always shaped by the same model template. A template change changes every vector: add a new model entry instead of editing one.
- **Search degrades, it does not fail**, when the question cannot be embedded: `mode: FULLTEXT`. Readiness depends on Postgres only (`postgres` is the one critical health check).
- **Default weights are vector only, because that is what was measured.** Change `search.weights` only after measuring the blend with `scripts/evaluate-search.mjs` against the real question set.
- **Scheduled runs are incremental only.** A first build and a backlog above `indexer.maxScheduledEmbeddings` need `POST /reindex`: a full embed takes the Ollama node for ~25 minutes and evicts its chat model.
- **Order in an indexing run is load-bearing**: documents, then deletions, then the cursor, then embeddings. A crash repeats the run from the old cursor; the embedder being down leaves chunks pending, never fails the run.
- **One indexer across pods**: the run holds a Postgres advisory lock; a pod that finds it taken skips (`job.run.skips{job.skip.reason=overrun}`), and `POST /reindex` on that pod answers `409` rather than a `202` for a run that never happens.
- **A run is abortable, and must stay so.** `$onDestroy` and a lost lock connection abort it; the indexer checks the signal between documents and batches and hands it to every GitHub and Ollama call. A new step in a run takes the signal too, or a deploy mid-run ends in the hard shutdown deadline. An aborted run records `INTERRUPTED`, not `FAILURE`.
- One trust domain (`AuthMethod.Idp`) on every controller class, `knowledge-base-api.reader` as the class-level floor, `knowledge-base-api.editor` added on the write routes, `knowledge-base-api.admin` on `POST /reindex`. Which knowledge bases a caller sees is each KB's `readers` list; an unreadable KB answers the same `404` as a missing one.
- Mappers are one-directional (storage or source → response). Writes never touch the index: they commit to the source and start an incremental run (`IndexingLoopService.trigger`), so the index has one writer, the run.
- **`version` is the source's own revision — for git the blob SHA — and the source checks it.** Never send the live SHA instead of the caller's (the last writer would win), and answer a refusal from the source (`DocumentWriteService`): `409` with the current document as the `CURRENT` entry of `errors` (Ts.ED's default exception body, no custom filter), `404`, or one retry when the blob is still the caller's. Writes run one at a time in a pod.
- **The write rules live in the API**: area rules, note rendering, the spec checks, secret refusal. A rule change here is a rule change for every client; keep it in step with the knowledge base's own checker.
- **`On-Behalf-Of` is checked in `DocumentValidationService`, not by its `@Pattern`**: Ts.ED does not validate header parameters. It reaches the commit message, so it must never hold a newline.
- **The request log names the caller and carries no body.** `LoggerProvider` forces `logger.requests.request` and `.response` off — a response is knowledge-base content — and its `metaProvider` adds `principalSubject`, `principalKind` and `principalIssuer` from `PrincipalService` to every line written during a request. Never add a token, a claim beyond those, or a body back; what a line holds is listed in the README's Telemetry section. A new log line written in a request inherits the caller for free; code that should not (a run started by a request) leaves the async context, as `IndexingLoopService.trigger` does.
